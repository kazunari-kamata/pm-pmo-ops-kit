# プロジェクトライフサイクルの使い方

テンプレートは、成果物を作ること自体ではなく、関係者間の合意と判断を残すために使用します。小規模案件では項目を統合し、大規模案件では粒度を分けてください。

| 工程 | 目的 | 最低限の確認 | 主なテンプレート |
| --- | --- | --- | --- |
| 構想・立上げ | 目的と責任を明確にする | 目的、範囲、スポンサー、主要制約が合意済み | 憲章、ステークホルダー、キックオフ |
| 要件定義 | 実現する価値を合意する | 要件、優先度、受入条件、除外範囲が確認済み | 要件定義、トレーサビリティ、意思決定ログ |
| 計画 | 実行可能な計画を作る | WBS、体制、リスク、連絡方法、承認が確認済み | WBS、RACI、RAID、コミュニケーション計画 |
| 設計・開発 | 品質と進捗を管理する | レビュー、課題対応、変更影響、進捗差異が確認済み | 設計レビュー、進捗報告、エスカレーション |
| テスト・移行 | 安全に利用開始する | テスト結果、受入、移行手順、ロールバックが確認済み | テスト計画、受入判定、移行計画 |
| 終結 | 引継ぎと学びを残す | 完了条件、残課題、運用移管、振り返りが確認済み | 完了報告、振り返り |

## 工程ゲートの原則

各工程の終了時には、次工程へ進む判断者、判断材料、未解決事項、条件付き承認の条件を意思決定ログへ記録します。承認されていない事項を「暗黙に了承された」と扱わないでください。

## 台帳の運用

リスク、課題、変更、決定は似ていますが目的が異なります。

- リスク: 将来起こり得る不確実性。発生前に対応方針を決めます。
- 課題: すでに発生し、対応が必要な事実。期限と担当者を持ちます。
- 変更: 合意済みの範囲・品質・費用・日程・体制を変える要求。影響評価と承認が必要です。
- 決定: 選択肢の比較を経て確定した判断。理由と決定者を残します。
